## 1. What `/fb-tarot` is, in one paragraph

A Facebook-ad quiz-bridge: she taps one of three face-down tarot cards, gets a short
reading, then hands into the main Evelyn chat funnel (`/chat`) where the sale happens.
A **lander** here is one entry in a hook registry (an ad question + its reading) — never
a new page, route, or component. All landers currently serve on one deck, `return-mhf`
(the Magician / Hanged Man / Fool, face down). Full architecture: `PRD-tarot-bridge.md`.

Two writing **methods** exist side by side, chosen per hook, both folding into the same
four registry beat-slots:

- **Natural Tarot-Cut** (`natural-tarot-cut.md`) — 7 cuts, the read *answers* her question.
- **Inherited Shadow** (`inherited-shadow-cut.md`) — 6 beats, the read *withholds* the
  answer behind a named block (the thing the upsell removes).

A hook can run Natural only, or both ("armed" — both reads exist, and a live A/B test,
`v1_tarot_shadow_2026`, splits traffic between them).

operator's explicit call this session: skip collision-checking, don't rewrite approved
copy to dodge it. If this bothers a future reviewer: the fix is rewording the *new* copy
to remove the overlap, never touching the old landers, and only with the operator's copy
sign-off (copy is transferred verbatim from the approved manuscripts, never paraphrased).

## 6. Extending this funnel next time

The process for adding new question-hooks (not new card art) is a Claude Code skill:
`.claude/skills/fb-tarot-hooks/`. It covers VOC sourcing, drafting to whichever method,
collision/guard checks, a human review gate, and wiring — read it before improvising a
new process. New card **art** (a new deck) is a different skill, `fb-tarot-add-card`.

Key files a change touches, in order:

1. `client/src/content/tarotReads.ts` — `TarotHook` union, `TAROT_HOOKS`, `HEADLINES`,
   `TAROT_QUESTION`, `RETURN_MHF.reads` (Natural), `RETURN_MHF.hookInstruction` if the
   default tap line is wrong for the new family, any reporting angle array.
2. `client/src/content/tarotReadsShadow.ts` — `SHADOW_READS`, if the hook runs Shadow too.
3. `server/lib/prompts.ts` — add to an existing frame Set if one fits, or build a new one
   plus its guard clause if the family needs rules no existing frame has (see the frame
   comments in that file — each documents exactly why it exists and what it added).
4. `server/routes.ts` — `validHooks`.
5. `scripts/lander-registry.mts` — regenerate the doc afterward; if the hook was staged
   via `DRAFT_CANDIDATES` first, remove it from there in the same pass that wires it live
   (the generator refuses a hook present in both).
6. If armed for Shadow and meant to go into `v1_tarot_shadow_2026`, append to that
   experiment's `scope.landers` in production — a deliberate, explicit DB write, not
   something to bundle into an automated script without a human confirming it first.

## 7. Standing safety invariants (unchanged by tonight's work)

- `cards-feels` and `cards-return` are protected controls — never rewritten, never armed.
  Enforced in code (`scripts/lander-registry.mts` exits 1 if either is armed).
- Arming a hook for Shadow never edits its Natural read — `DECKS[deck].reads` is the
  30% control arm and must stay byte-identical to what serves today.
- Copy is transferred verbatim from an approved manuscript. Never paraphrased, never
  "fixed" to satisfy a checker, never normalized for contractions.
- No deploy, no push to a main/production branch, no starting an experiment — all three
  stay explicit, separate, operator-triggered actions.
